# 模範解答

## 問1

### (1) 正解：C

#### この問題で確認したいこと

テンプレート化された基底クラスでは、既定では名前探索が行われないこと。

#### 解説

`MsgSender<Company>` はテンプレートパラメータに依存する基底である。`Company` ごとの**全特化**でインターフェースが変わり、`sendClear` が無いこともあり得る。そのため準拠コンパイラは、特に指示がなければそのような基底の中を調べず、`sendClear` を「存在しない名前」として扱う。

|選択肢|判定|理由|
|-------|-------|-------|
|A|×|非テンプレート基底からは普通に呼べる。問題はテンプレート化された基底に特有|
|B|×|非仮想でも基底メンバは呼べる。名前探索の話であり仮想性の話ではない|
|C|○|依存する基底は特化で変わり得るため、既定では探索しない|
|D|×|問題コードでは可視性は示しておらず、本質は名前探索|

### (2) 正解：B

#### この問題で確認したいこと

全特化によって基底のインターフェースが変わり得ること。

#### 解説

`template<> class MsgSender<CompanyZ>` は、`CompanyZ` を与えたときの**特別版**（全特化）である。ここでは `sendClear` が無い。したがって `LoggingMsgSender<CompanyZ>` の基底には `sendClear` が無く、コンパイラが「テンプレート化された基底にそのメンバがある」と決め打ちできない理由の具体例になる。

|選択肢|判定|理由|
|-------|-------|-------|
|A|×|他の `Company` では一次テンプレートが使われる|
|B|○|特化でメンバが欠ける例が、探索を控える根拠になる|
|C|×|全特化ではインターフェースを変えられ、メンバを省くこともできる|
|D|×|どの特化を使うかはコンパイル時に決まり、名前探索に直結する|

### (3) 正解：D

#### この問題で確認したいこと

テンプレート化された基底の名前を使える3つの手段。

#### 解説

次のいずれでも、コンパイラに「その名前は基底側を見る」と伝えられる。

1. `this->` を付け、依存名として扱う
2. `using` 宣言で基底の名前を派生クラスのスコープに持ち込む
3. 基底クラス名で明示的に修飾する

|選択肢|判定|理由|
|-------|-------|-------|
|A|×|2 と 3 も有効|
|B|×|3 も有効|
|C|×|1 も有効|
|D|○|3つすべてが正しい手段|

## 問2 正解：B

### この問題で確認したいこと

明示修飾は仮想呼び出しを抑止すること。

### 解説

`this->sendClear(info)` と、`using` のあとでの `sendClear(info)` は、通常のメンバ呼び出しとして扱われ、`sendClear` が仮想なら動的束縛の対象になり得る。一方 `MsgSender<Company>::sendClear(info)` は修飾付き呼び出しであり、仮想関数でも**そのクラスの版を直接呼ぶ**（動的束縛しない）。3つの手段は「名前を基底から見えるようにする」点では同じだが、仮想関数に対する振る舞いは明示修飾だけが異なる。

|選択肢|判定|理由|
|-------|-------|-------|
|A|×|明示修飾は動的束縛を抑止する|
|B|○|`this->` / `using` と明示修飾の差を正しく述べている|
|C|×|`using` 自体は仮想性を無効にしない|
|D|×|`this->` は仮想呼び出しを抑止しない|
